# Benchmarks

Scripts for the four experimental scenarios from the assignment, once for
each broker. All scripts are pure bash and drive the stack purely through:

- the **ingestion** service's HTTP control API (`/simulate/start`, `/simulate/stop`)
- `docker exec` into `project-two-postgres` to count rows in `readings`
- `docker stats` for CPU/RAM/network footprint
- `docker network disconnect/connect` for Scenario B
- `kafka-consumer-groups.sh --describe` for consumer lag (Kafka only)

No extra tooling (emqtt-bench, k6, kafka-producer-perf-test) is required —
load is generated by the ingestion service itself, which already exposes the
QoS / `acks` knobs needed for the comparison.

## Prerequisites

1. Docker Desktop running, with the compose stack up:
   ```bash
   docker compose up -d --build
   ```
2. Run scripts from a bash shell (Git Bash / WSL on Windows, or any Linux/macOS shell).
3. `curl`, `awk`, `docker`, `docker compose` available on PATH.
4. Verify the compose network name matches `COMPOSE_NETWORK` (default
   `project-two_default`) — required for Scenario B:
   ```bash
   docker network ls | grep project-two
   ```
   If it differs, export `COMPOSE_NETWORK=<name>` before running scenario B.

## What each script does

| Scenario | Script | What it measures |
|---|---|---|
| A — Massive Sensor Ingestion | `scenario_a.sh [qos\|acks] [duration_s]` | Throughput (rows/s) and loss % for 100 / 1000 / 10000 simulated devices |
| B — Edge Connectivity Failures | `scenario_b.sh [qos\|acks] [devices]` | Recovery of persisted-row count after a 30s `docker network disconnect` on the ingestion container |
| C — Burst Event Load | `scenario_c.sh [qos\|acks]` | Backlog growth/drain when load jumps from ~50 msg/s to ~5000 msg/s and back |
| D — Real-Time Alerting | `scenario_d.sh [qos\|acks]` | End-to-end latency from reading generation to `[ALERT]` log line (forced temperature > 50°C) |

`scenario_a/b/c/d.sh` live under `benchmarks/mqtt/` and `benchmarks/kafka/`.
Each one **recreates** the `ingestion`, `analytics`, and `storage` containers
with the requested broker setting before running, so the rest of the stack
(`postgres`, `mosquitto`, `kafka`) can stay up across the whole benchmark
session.

## Running the full sweep

MQTT — QoS 0, 1, 2:

```bash
for qos in 0 1 2; do
  ./benchmarks/mqtt/scenario_a.sh "$qos"
  ./benchmarks/mqtt/scenario_b.sh "$qos"
  ./benchmarks/mqtt/scenario_c.sh "$qos"
  ./benchmarks/mqtt/scenario_d.sh "$qos"
done
```

Kafka — acks 0, 1, all (`-1`):

```bash
for acks in 0 1 -1; do
  ./benchmarks/kafka/scenario_a.sh "$acks"
  ./benchmarks/kafka/scenario_b.sh "$acks"
  ./benchmarks/kafka/scenario_c.sh "$acks"
  ./benchmarks/kafka/scenario_d.sh "$acks"
done
```

> Note: `KAFKA_ACKS` must be numeric (`0`, `1`, `-1`) — the ingestion
> publisher does `parseInt(process.env.KAFKA_ACKS)`, where `-1` means
> `acks=all`.

Scenario A with 10000 devices and the full sweep above takes a while
(each scenario_a run is ~3 * (duration + buffer) seconds, default
duration 30s). Reduce the duration for a quick smoke test, e.g.:

```bash
./benchmarks/mqtt/scenario_a.sh 1 10
```

## Output

All results are written to `docs/results/<scenario>/`:

- `scenario_a/`: `*_summary.csv` (devices, expected vs received, loss %,
  throughput) + `*_dockerstats.csv` per device count
- `scenario_b/`: `*_timeline.csv` (elapsed seconds, phase, cumulative rows)
- `scenario_c/`: `*_timeline.csv` + `*_dockerstats.csv`
- `scenario_d/`: `*_alerts.log` (raw analytics log lines incl. `avg_latency`)

Kafka scripts additionally print `kafka-consumer-groups.sh --describe`
output for the `project-two-storage` and `analytics-group` consumer groups
to stdout — redirect to a file if you want to keep it, e.g.:

```bash
./benchmarks/kafka/scenario_a.sh 1 30 | tee docs/results/scenario_a/kafka_acks1_run.log
```

## Troubleshooting

- **`docker network disconnect` fails in Scenario B**: the compose network
  name doesn't match `COMPOSE_NETWORK`. Run `docker network ls`, find the
  network containing `project-two-ingestion`, and re-run with
  `COMPOSE_NETWORK=<that name>`.
- **`reading_count` returns empty**: `project-two-postgres` isn't healthy yet,
  or `POSTGRES_USER`/`POSTGRES_DB` differ from `.env` — override
  `DB_USER`/`DB_NAME` env vars for the scripts accordingly.
- **High device counts (10000) time out or saturate the host**: this is
  expected — that's the point of Scenario A. Record the loss % and note CPU
  saturation in the report rather than trying to eliminate it.
